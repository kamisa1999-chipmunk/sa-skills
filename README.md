# SA Review

`sa-review` — skill для ревью системной аналитики по Jira-задаче и связанным спецификациям.

Он собирает контекст изменения, проходит связанные Jira-задачи и Confluence-страницы, сверяет применимые артефакты с SA-чек-листом, ищет противоречия между контрактами и сценариями, отделяет подтверждённые замечания от вопросов и формирует итог, который можно использовать как основу для ревью аналитика.

Skill пишет про состояние артефактов, а не про человека. Он не придумывает спецификацию за аналитика и не изменяет Jira/Confluence без отдельного подтверждённого шага публикации.

---

## Быстрый старт

Если Jira и Confluence уже доступны в Cursor через MCP / connector / встроенные tools:

```bash
git clone https://github.com/kamisa1999-chipmunk/sa-skills.git
cd sa-skills
mkdir -p ~/.cursor/skills
ln -s "$(pwd)/skills/sa-review" ~/.cursor/skills/sa-review
```

Перезапусти Cursor или открой новый Agent chat, затем попроси, например:

```text
Сделай ревью CAT1-4728
```

или:

```text
Проверь мою аналитику CAT1-4728 перед ревью
```

Если Jira/Confluence через MCP недоступны, настрой local CLI fallback — инструкция ниже.

Клиенты Jira/Confluence и скиллы записи (`jira-write`, `jira-history`) живут в соседнем репозитории [`jira-write`](https://github.com/kamisa1999-chipmunk/jira-write). Для обычного ревью через MCP он не обязателен.

---

## Что умеет skill

`sa-review` не проверяет одну страницу изолированно. Он строит карту изменения и по мере необходимости проходит экосистему задачи:

- основную Jira-задачу;
- связанные / дочерние Jira-задачи;
- Confluence-спецификации и связанные страницы;
- API-контракты и модели;
- UI / frontend / mobile сценарии;
- Admin UI и Admin API;
- события и аналитику, если этот контур применим;
- ошибки, edge cases и зависимости;
- задачи разработки и тестирования;
- соответствие типа спецификации утверждённому шаблону;
- противоречия между несколькими источниками.

Перед выдачей результата skill отдельно проверяет coverage и reconciliation, чтобы случайно не потерять уже найденный gap при группировке замечаний.

## Режимы

| Режим | Когда использовать | Что отличается |
|---|---|---|
| `self-check` | «проверь мою аналитику», «готова ли к ревью», «что я не учла» | Самопроверка без истории сотрудника и без записи в Jira |
| `review` | «сделай ревью», «поревьюй», «можно ли отдавать в разработку» | Обычное техническое ревью |
| `lead-review` | «лид-ревью», «с историей», «повторились ли ошибки» | Сначала полный технический review, затем сопоставление с историей. Карточка пишется, только если она есть в workspace |

Если режим не указан явно и задача выглядит как обычное ревью, используется `review`.

## Что нужно для работы

### Обязательно

- Cursor с Agent mode и поддержкой skills;
- сам `sa-review`, доступный Cursor как skill;
- доступ к Jira-задаче;
- доступ к связанным Confluence-страницам;
- файл SA-чек-листа из этого репозитория: `skills/sa-review/checklist-close-sa.md`.

### Доступ к Jira и Confluence

Skill поддерживает два режима. Критерии ревью в них одинаковые.

#### Вариант A — MCP / connector / встроенные tools

Это рекомендуемый вариант, если Jira и Confluence уже подключены к Cursor.

Дополнительные Python-клиенты и локальные токены для чтения не нужны, если tool умеет получить необходимые данные.

Skill ожидает, что источник может прочитать как минимум:

**Jira:**

- summary;
- description;
- issue type;
- links / children / related issues;
- comments — когда они нужны для конкретного критерия;
- parent / epic — при необходимости.

**Confluence:**

- title;
- URL;
- актуальное содержимое страницы;
- version / date — если источник их отдаёт;
- labels / тип страницы — если доступны.

Если MCP/connector не отдаёт часть обязательных полей, skill может точечно добрать их другим доступным способом. Если данных всё равно недостаточно, он должен вернуть `NEEDS_CLARIFICATION`, а не считать ветку проверенной.

#### Вариант B — local CLI fallback

Если Jira/Confluence не подключены через MCP, используй клиенты из соседнего репозитория [`jira-write`](https://github.com/kamisa1999-chipmunk/jira-write). Этот репозиторий клиентов не дублирует.

```bash
git clone https://github.com/kamisa1999-chipmunk/jira-write.git
cd jira-write
python3 -m pip install -r scripts/requirements.txt
cp scripts/.env.example scripts/.env
export JIRA_WRITE_REPO_DIR="$(pwd)"
```

Для Jira нужны:

```text
JIRA_URL=...
JIRA_PROJECT=...
JIRA_PAT=...
```

или Basic Auth через `JIRA_USERNAME` + `JIRA_PASSWORD`.

Для Confluence используется отдельный доступ:

```text
CONFLUENCE_URL=...
CONFLUENCE_PAT=...
```

или `CONFLUENCE_USERNAME` + `CONFLUENCE_PASSWORD`.

Jira PAT и Confluence PAT — разные токены. Не коммить `.env` и не передавай токены модели в чат.

Проверить Jira можно командой:

```bash
python3 "$JIRA_WRITE_REPO_DIR/scripts/cli/get_issue.py" CAT1-1234
```

Проверить Confluence по `pageId`:

```bash
python3 ~/.cursor/skills/sa-review/scripts/dump_confluence_page.py PAGE_ID
```

GitLab/GitHub-доступ для обычного `review` не обязателен. Он нужен только для отдельных сценариев, где анализируется история задачи вместе с MR.

Самый простой вариант — symlink на папку skill:


## Как запускать

Минимальный запрос:

```text
Сделай ревью CAT1-4728
```

Самопроверка:

```text
Проверь мою аналитику CAT1-4728 перед ревью
```

Тимлидское ревью с историей:

```text
Сделай lead-review CAT1-4728 и после технического ревью проверь, повторялись ли такие ошибки раньше
```

Можно также попросить:

```text
Поревьюй спецификации по CAT1-4728 и покажи замечания по одному
```

или:

```text
Покажи все замечания сразу
```

Skill сначала формирует полный набор findings, поэтому команды «дальше» / «следующий» должны только показывать уже готовую очередь, а не запускать анализ заново.

## Как проходит ревью

Упрощённо pipeline выглядит так:

```text
режим
  ↓
Jira + SA checklist
  ↓
карта изменения
  ↓
applicability
  ↓
Jira / Confluence / связанные спецификации
  ↓
evidence
  ↓
findings
  ↓
coverage gate
  ↓
reconciliation
  ↓
категоризация
  ↓
замечания + вопросы + итоговый текст
```

Важные принципы:

- finding появляется только после проверки evidence;
- неизвестная применимость → вопрос / `NEEDS_CLARIFICATION`, а не выдуманный дефект;
- один root cause → один finding;
- независимые проблемы не склеиваются только потому, что находятся на одной странице;
- связанная Jira-задача сама может активировать отдельную ветку проверки;
- история сотрудника не влияет на поиск текущих дефектов;
- никакой автоматической публикации.

---

## Что получает пользователь

В зависимости от режима выдача может быть пошаговой или сразу целиком.

Типичный finding содержит:

```text
На схеме BFF отсутствует вызов GetProductNavigation, хотя алгоритм и mapping name ← header на него опираются.

Источник: <ссылка на BFF> + <ссылка на GetProductNavigation>

Ожидаемое состояние: схема и алгоритм описывают одну последовательность вызовов.
```

Если доказательств недостаточно, это должно выглядеть как вопрос:

```text
MiniApp входит в scope изменения? Он присутствует в дереве BFF, но не описан на feature page.
```

В конце skill может собрать читаемый текст для отправки аналитику. Публикация в Jira выполняется только отдельным подтверждённым действием.

---

## Что skill принципиально не делает

- не пишет спецификацию за аналитика;
- не выбирает «правильную» сторону противоречия без evidence;
- не превращает неизвестный контекст в ISSUE;
- не оценивает автора задачи как человека;
- не ищет ошибки по истории сотрудника;
- не меняет Jira и Confluence автоматически;
- не обязан открывать весь репозиторий и все ссылки подряд;
- не гарантирует 100% обнаружение всех возможных проблем.

Качество результата зависит от доступности связанных артефактов и от выбранной модели.

## Рекомендуемая модель

На текущем внутреннем benchmark для одной реальной SA-задачи лучший совокупный результат показал **Grok 4.6 High**.

Он собрал почти весь полезный union предыдущих прогонов, сохранил глубокие контрактные находки и дал несколько дополнительных проблем, которые другие прогоны не заметили. При этом по фактическому Cursor usage стоимость оказалась низкой.

Практический выбор сейчас такой:

| Модель / режим | Когда использовать |
|---|---|
| **Grok 4.6 High** | Полное ревью перед передачей аналитики дальше; рекомендуемый default для качества |
| **Grok 4.6 Medium** | Когда важнее скорость первого ответа и нужен более дешёвый/быстрый exploratory review |

У High на тестовой задаче был заметно более долгий старт до первого finding, поэтому это не обязательно лучший режим для короткой проверки одной страницы.

Это эмпирическая рекомендация по ограниченному benchmark, а не гарантия, что другая модель не окажется лучше на другом типе задачи.

## Как тестировали

Skill несколько раз прогонялся на одной и той же реальной SA-задаче после последовательных доработок.

В сумме прогоны находили, среди прочего:

- несовпадающие идентификаторы одного виджета между BFF / SDK / Admin / DB;
- несовпадение sequence diagram и алгоритма;
- HTTP-страницу, фактически описывающую gRPC;
- противоречия BFF ↔ Catalog ↔ proto;
- незакрытые `countryISOCode`, `itemId`, `useCrossCountry`;
- чужие модели в Admin API / AdminApp;
- пустые implementation tasks;
- вопросы по MiniApp и границе со старым контуром;
- внутреннее расхождение таблицы ответа BFF и JSON-примеров.

Разные модели находили разные части картины. Именно поэтому в skill появились отдельные coverage gate и reconciliation, а чтение Jira/Confluence было отвязано от конкретного локального клиента.

## Troubleshooting

### Cursor не видит skill

Проверь symlink:

```bash
ls -la ~/.cursor/skills/sa-review
```

и открой новый Agent chat.

### Jira не читается

Если используешь MCP/connector — сначала проверь доступ к самой Jira-задаче через этот tool.

Если local fallback — проверь `.env` и команду:

```bash
python3 "$JIRA_WRITE_REPO_DIR/scripts/cli/get_issue.py" CAT1-1234
```

### Confluence не читается

Для MCP/connector проверь, что tool умеет читать содержимое страницы, а не только её metadata.

Для local fallback:

```bash
python3 ~/.cursor/skills/sa-review/scripts/dump_confluence_page.py PAGE_ID
```

Если появляется `Не найден confluence_client`, клонируй [`jira-write`](https://github.com/kamisa1999-chipmunk/jira-write) и задай `JIRA_WRITE_REPO_DIR` на его корень.

### Модель пометила ветку `checked`, хотя данных не было

Это не ожидаемое поведение. Если источник не отдаёт обязательные поля и их нельзя добрать, ветка должна остаться `NEEDS_CLARIFICATION`.

### Review слишком долго запускается

Полное ревью намеренно сначала собирает всю очередь findings и проходит coverage/reconciliation. Для более быстрой предварительной проверки можно использовать Grok 4.6 Medium, а High оставить для финального review.

## Безопасность

- не коммить `.env`;
- не вставляй PAT/пароли в prompt;
- Jira и Confluence могут использовать разные токены;
- `sa-review` работает в read-only режиме;
- публикация замечаний — отдельный сценарий и только после подтверждения.
