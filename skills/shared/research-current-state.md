# Research и current state

Общие правила исследования для `sa-spec`. `sa-review` проверяет те же классы рисков своим пайплайном (`architecture-validation.md`, чек-лист, evidence). Этот файл не заменяет ревью и не копирует его.

Читать в `sa-spec` на этапе research, до `artifact-plan.md`. В `sa-review` не подменять им checklist и architecture validation.

## Когда current state обязателен

Если изменение затрагивает поведение системы, API, gRPC, контракты, хранение, интеграции, клиентов, алгоритмы выбора / fallback / priority, admin-flow.

Иначе достаточно источников задачи и существующих спецификаций. Не раздувать исследование «на всякий случай».

## Что смотреть

- Jira Story и связанные requirements;
- feature page и feature notes — один релевантный файл, не все фичи;
- существующие Confluence-спецификации и контракты;
- current state по коду, если документ молчит или нужно сверить факт;
- producer → contract → consumer для изменяемого интерфейса;
- web / iOS / Android / BFF / другие сервисы — только при подтверждённой зависимости;
- storage и domain model;
- admin flow;
- связанные версии API / gRPC;
- существующие алгоритмы, fallback, priority, filtering, grouping, timers, switching — если они относятся к изменению.

## Как расширять scope

Не читать все репозитории подряд.

Другой компонент открывать только если зависимость подтверждена одним из:

- документация;
- кодовый вызов;
- контракт;
- явная архитектурная связь.

Нет репозитория или страницы и проверить доступными источниками нельзя:

- статус `Cannot verify`;
- не искать похожую реализацию в случайных репозиториях;
- не делать вывод, что реализации нет.

## Что учитывать, чтобы черновик выдерживал `sa-review`

`sa-spec` готовит артефакты так, чтобы они изначально попадали в ожидания ревью. Ревью остаётся независимой проверкой и может найти ошибки.

На подготовке держать в голове, не прогоняя review pipeline:

- откуда взято бизнес-правило;
- requirement отдельно от выбранного решения;
- allowed outcomes отдельно от алгоритма выбора;
- границы ответственности компонентов;
- обязательные спецификации по типу;
- одно logical field одинаково названо и описано в связанных контрактах;
- producer / contract / consumer;
- backward compatibility и существующие клиенты;
- связанные сценарии;
- где документ должен лежать (feature page, Jira, method spec);
- корпоративный шаблон типа.

Неподтверждённое не записывать как факт. Нехватка данных — вопрос `Q-NNN` или `Cannot verify`, не догадка.
