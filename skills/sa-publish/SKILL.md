# SA-publish

Отвечает только за доставку уже подготовленных артефактов. Профиль `publish` — economical. Содержательных решений нет. Роли: [../shared/model-routing.md](../shared/model-routing.md).

Две фазы. Их не смешивать.

**Draft.** Существующая страница: применить redline (`{+новый+}`, `{-старый-}`), текст не удалять, маркер `Generated draft` оставить. Новая страница: создать из шаблона с тем же маркером. Статус артефакта остаётся `Generated draft` / `Reviewed draft` / `Ready for review`. В плане `Фаза: draft`.

**Finalize.** Только после чтения, `sa-review` и явного утверждения. Статус `Approved`, в плане `Фаза: finalize`. Тогда зелёный текст становится обычным, красный зачёркнутый удаляется, маркер черновика снимается, статус становится `Published`.

Маркеры и смысл типов правок — `sa-spec/redline.md`. Скрипт сам конвертирует маркеры: на draft красит, на finalize снимает.

Он не должен:

* генерировать требования;
* дописывать спецификацию;
* принимать архитектурные решения;
* исправлять замечания ревью самостоятельно.

Его роль:

```text
утверждённый локальный артефакт
→ проверка
→ preview
→ подтверждение
→ публикация
→ фиксация результата
```

Токены не читать и не показывать. Без явного подтверждения ничего не писать во внешние системы.

Структура файлов: [workspace.md](workspace.md) (канон тот же, что у `sa-spec`).

## Источник

Рабочая директория:

```text
sa-work/<ISSUE-KEY>/
```

Главный вход:

```text
publish-plan.md
```

Не брать файлы из других мест как источник публикации. Если плана нет — остановиться и сказать, что сначала нужен `sa-spec`.

## Связка скиллов

| Skill        | Ответственность                            |
| ------------ | ------------------------------------------ |
| `sa-spec`    | исследует, задаёт вопросы, пишет черновики |
| `sa-review`  | проверяет качество и полноту               |
| `sa-publish` | безопасно публикует утверждённое           |

`sa-publish` не должен заменять `jira-write`.

После публикации можно **предложить** подготовить через `jira-write`:

* ссылки на новые спецификации;
* обновление description;
* комментарий о готовности аналитики.

Только отдельным подтверждаемым действием.

## `publish-plan.md`

Для каждого артефакта — блок из [workspace.md](workspace.md): путь, статус, назначение, операция, pageId, версия источника, git path.

## Проверка перед публикацией

Для каждого файла проверить:

* фаза понятна: `draft` или `finalize`;
* для draft статус `Generated draft`, `Reviewed draft` или `Ready for review`;
* для finalize статус `Approved` (старое «Утверждено» скрипт принимает как finalize);
* нет блокирующих вопросов (`questions.md`);
* нет незавершённого review (блокирующие замечания в `review/`);
* файл существует;
* цель публикации определена;
* операция понятна: создать / обновить;
* формат совместим с целевой системой.

Если что-то не выполнено — не публиковать этот артефакт (пропуск в preview, не ошибка всего пакета).

## Проверка конфликтов

Перед обновлением существующего документа обязательно получить его актуальное состояние.

Confluence:

```bash
python3 ~/.cursor/skills/sa-review/scripts/dump_confluence_page.py PAGE_ID
```

Сравнить с версией, на основании которой создавался локальный черновик (`Версия источника при загрузке`).

Если внешний документ изменился:

```text
не перезаписывать
→ показать конфликт
→ остановить публикацию этого файла
```

Пример:

```text
Страница GetLabels изменилась после начала работы.

Локальная база: версия 17
Текущая Confluence: версия 19

Публикация остановлена.
```

Git: `git fetch` + сравнить целевой файл на remote с хешем/содержимым на момент копирования в локальный черновик, если оно зафиксировано. Если неизвестно — показать diff относительно текущей ветки-цели и не коммитить без подтверждения.

## Preview

До любого изменения показать полный план.

CLI для Confluence (по умолчанию ничего не пишет):

```bash
python3 ~/.cursor/skills/sa-publish/scripts/publish_confluence.py \
  --work sa-work/<ISSUE-KEY>
```

Пример плана:

```text
К публикации готово 4 артефакта:

1. get-labels-v3.md
   → Confluence
   → создать страницу GetLabels V3

2. product-label-store.md
   → Confluence pageId=740496592
   → обновить

3. feature.md
   → Confluence pageId=819326063
   → обновить

4. media.md
   → Git
   → catalog-docs/docs/grpc/media.md
   → обновить

Пропущено:
- rtl.md — статус «Есть открытые вопросы»
```

После этого запросить явное подтверждение.

## Подтверждение

Публикацию начинать только после явного ответа пользователя.

Поддержать:

* «публикуй всё»;
* «только 1 и 3»;
* «Confluence публикуй, Git пока нет»;
* «покажи diff по второму».

Не трактовать «ок» / «спасибо» как разрешение публиковать.

## Confluence

Поддержать:

### Создание страницы

Два шага:

1. создать страницу **из space-шаблона** BIZ (не пустую);
2. заполнить плейсхолдеры и именованные секции из локального Markdown.

Нужно знать:

* parent page;
* title;
* тип: `http` / `grpc` / `feature` / `db` / `kafka` / `ui` / `admin` (из пути `specs/…` или поля `Тип` в плане);
* содержание с YAML-шапкой (`метод`, `путь`, `описание`, …) и заголовками секций как в шаблоне (`Алгоритм работы`, `Запрос v1`, …).

Карта шаблонов: `sa-publish/space-templates.json`. Живой шаблон — `/rest/experimental/template/{id}`; если API недоступен — снимок в `sa-publish/templates/{id}.json`.

Нельзя подменять всё тело страницы «голым» HTML из Markdown: обвязка шаблона (info, details, LinkGraph, PlantUML) должна остаться.

### Обновление страницы

Нужно знать:

* `pageId`;
* текущую версию;
* базовую версию локального черновика.

Обновление пишется поверх текущего тела страницы, не поверх пустого шаблона. В локальном Markdown на draft должен быть redline нужного блока, включая старый текст в `{- -}`, иначе секция затрётся новым абзацем.

Нельзя молча перезаписывать изменённую страницу. Нельзя снимать redline на фазе draft.

После подтверждения:

```bash
python3 ~/.cursor/skills/sa-publish/scripts/publish_confluence.py \
  --work sa-work/<ISSUE-KEY> \
  --only 1,3 \
  --apply
```

`--only` — номера из preview или относительные пути файлов.

Скрипт создаёт страницу из шаблона, затем заполняет секции. Если именованную секцию нельзя сопоставить — её содержание дописывается в конец, шаблон не стирается. Если разметка всё равно ломается — остановить этот файл и показать причину.

## Git

Предпочтительная схема:

```text
создать ветку
→ внести файлы
→ показать diff
→ commit
→ при необходимости PR
```

Не пушить напрямую в protected/main, если рабочий процесс репозитория предполагает review.

Конкретное поведение определять по правилам целевого репозитория (CONTRIBUTING / protected branches). Не коммитить секреты. Не использовать токен GitLab из `.env` без нужды: локальный `git` + существующий remote.

Этот CLI Confluence Git не публикует: Git делает агент командами `git` в целевом клоне, после preview diff.

## Частичная публикация

Разрешить публиковать не весь пакет сразу.

После частичной публикации `publish-plan.md` должен отражать состояние каждого документа.

Например:

```text
feature.md — опубликовано
get-labels-v3.md — опубликовано
media.md — утверждено, не опубликовано
rtl.md — есть открытые вопросы
```

## После публикации

Для опубликованного артефакта записать:

```markdown
Статус: Published
Дата: ...
Цель: ...
URL/pageId/path: ...
Версия после публикации: ...
Commit: ...
```

## Итоговый отчёт

Пример:

```text
Публикация завершена.

Опубликовано: 3
- Feature page
- GetLabels V3
- ProductLabel_{storeId}

Не опубликовано: 1
- Media — пользователь исключил из текущей публикации

Конфликтов: 0
Ошибок: 0
```

Если есть конфликт — явно показать.

## Порядок работы

```text
SA-publish:
- [ ] Рабочая директория и publish-plan.md найдены
- [ ] questions.md: нет статуса «открыт» типа «блокирующий»
- [ ] Проверка каждого пункта плана
- [ ] Актуальные версии Confluence / Git для операций «обновить»
- [ ] Preview пользователю
- [ ] Явное подтверждение (что именно публиковать)
- [ ] Apply только выбранного
- [ ] Обновить publish-plan.md
- [ ] Итоговый отчёт
- [ ] Предложить jira-write (не выполнять без отдельного «да»)
```

## Ограничения

Нельзя:

- публиковать без preview и явного подтверждения;
- публиковать finalize при статусе ниже `Approved`;
- на draft удалять старый текст или снимать redline;
- чинить findings ревью в момент публикации;
- перезаписывать страницу при расхождении версий;
- дописывать или «улучшать» спецификацию по дороге;
- пушить в protected/main в обход review;
- заводить/менять Jira вместо `jira-write`.
