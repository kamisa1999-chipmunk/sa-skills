# SA-spec

Подготовка системной аналитики и спецификаций на основании доступных источников.

Должен:

* собирать контекст задачи;
* определять, какие артефакты нужны;
* находить существующую архитектуру и аналогичные спецификации;
* формировать локальные Markdown-черновики;
* выявлять противоречия и недостающие решения;
* задавать пользователю вопросы по всему, что невозможно определить однозначно;
* после ответов актуализировать спецификации;
* перед передачей результата прогонять его через `sa-review`.

`sa-spec` **не публикует** изменения в Confluence/Git. Публикация — скилл `sa-publish`.

Структура файлов: [workspace.md](workspace.md). Загрузка источников: [sources.md](sources.md).

В пользовательском выводе — русские названия. Токены не читать и не показывать.

## Основной принцип

Skill не принимает самостоятельно продуктовые, архитектурные или контрактные решения, если они не следуют однозначно из подтверждённых источников.

Если информации недостаточно:

```text
не придумать
→ зафиксировать неопределённость
→ сформулировать вопрос
→ получить решение
→ внести его в артефакты
```

## Связка скиллов

```text
Jira / notes / Confluence / Git
            ↓
         sa-spec
            ↓
   локальные md-файлы
            ↓
        вопросы
            ↓
        решения
            ↓
        sa-review
            ↓
      утверждение
            ↓
       sa-publish
            ↓
     Confluence / Git
```

| Skill        | Ответственность                            |
| ------------ | ------------------------------------------ |
| `sa-spec`    | исследует, задаёт вопросы, пишет черновики |
| `sa-review`  | проверяет качество и полноту               |
| `sa-publish` | безопасно публикует утверждённое           |

Не подменять `jira-write`, `jira-history`, `sa-publish`. Feature notes предлагать обновить, не публиковать.

## Режимы

Определить режим **до** генерации спецификаций.

### Полная аналитика

Примеры:

```text
собери аналитику по CAT2-XXXX
подготовь спецификации по CAT2-XXXX
разбери CAT2-XXXX как аналитик
```

Skill определяет полный необходимый набор артефактов.

### Конкретная спецификация

```text
сделай HTTP-спеку для CAT2-XXXX
подготовь gRPC по CAT2-XXXX
опиши БД для CAT2-XXXX
сделай спецификацию админки
```

Работает только с выбранным артефактом, но проверяет связанные контракты.

### Доработка существующей спецификации

```text
обнови спецификацию под CAT2-XXXX
дополни текущую аналитику
```

Сначала определить текущее состояние и изменения, затем предложить обновлённую локальную версию.

### Разложение фичи

```text
разложи CAT2-XXXX на спецификации
какие документы нужны для этой фичи
```

Ничего не писать сразу. Выдать карту необходимых артефактов.

### Только открытые вопросы

```text
собери вопросы по CAT2-XXXX
что нужно решить перед аналитикой
```

Провести исследование, но не генерировать итоговые спеки.

## Порядок работы

Копировать и отмечать:

```text
SA-spec:
- [ ] Режим определён
- [ ] Рабочая директория sa-work/<ISSUE-KEY>/
- [ ] Уровень 1: Jira + чек-лист + прямые ссылки
- [ ] context.md (черновик)
- [ ] Карта артефактов (создать / обновить / не трогать)
- [ ] Уровень 2–4 по необходимости
- [ ] Аналоги 1–3 для новых типов
- [ ] questions.md (полный список, дедуп)
- [ ] Диалог по вопросам (если не режим «только карта»)
- [ ] Черновики specs/ (если режим это предполагает)
- [ ] decisions.md по закрытым вопросам
- [ ] sa-review self-check → review/self-check.md
- [ ] publish-plan.md
```

В режиме «разложение» остановиться после карты. В режиме «только вопросы» — после `questions.md` и диалога, без итоговых спек.

## Генерация спецификации

Формировать документ по существующему шаблону (живая страница Confluence; если недоступна — локальный снимок, см. [sources.md](sources.md) и [templates/README.md](templates/README.md)).

Если шаблона нет — по аналогичным документам и SA-чек-листу.

Каждый факт должен относиться к одной из категорий:

```text
подтверждено источником
следует однозначно из нескольких источников
решено пользователем
открытый вопрос
```

Не вставлять догадки как утверждения.

Писать только в `sa-work/<ISSUE-KEY>/`. Существующие страницы Confluence/Git не менять.

## Работа с вопросами

Все неразрешённые места записывать в `questions.md`. Шаблон — [workspace.md](workspace.md).

### Диалог

Сначала собрать **полный список** вопросов.

Перед показом:

* удалить дубли;
* объединить вопросы, зависящие от одного решения;
* отсортировать блокирующие выше остальных.

Если вопросов 1–3 — показать сразу.

Если 4 и более:

1. показать краткий список заголовков;
2. указать общее количество;
3. затем разбирать вопросы **по одному**.

Пример:

```text
Нашла 7 открытых вопросов:

1. Источник storeId
2. Поведение при неизвестном регионе
3. Момент переключения коллекций
...

Начну с блокирующих.

Вопрос 1 из 7:
...
```

### Ответ пользователя

Пользователь может:

* дать решение;
* сказать, как будет решать вопрос дальше;
* вынести за рамки;
* оставить открытым;
* отложить.

Поддерживаемые статусы:

```text
Открыт
Решён
Требует внешнего уточнения
Вынесен за рамки
Отложен
```

Если пользователь говорит:

> спрошу backend

записать:

```text
Статус: требует внешнего уточнения
Следующее действие: уточнить у backend
Ответственный: пользователь
```

Не требовать немедленного ответа. Не блокировать всю работу, если остались только неблокирующие.

## После решения вопроса

1. обновить `questions.md`;
2. добавить решение в `decisions.md`;
3. обновить все затронутые спецификации;
4. проверить связанные артефакты на противоречия;
5. продолжить со следующим вопросом.

## Самопроверка

Когда блокирующие вопросы закрыты, запустить `sa-review` в режиме самопроверки на **локальные** артефакты (`sa-work/<ISSUE-KEY>/specs/` + Jira). Следовать `SKILL.md` скилла `sa-review`.

Результат сохранить:

```text
review/self-check.md
```

Если найдены новые неопределённости — вернуть их в `questions.md`.

Не считать спецификацию готовой только потому, что текст сформирован.

После самопроверки статус артефакта: «Готово к ревью» или «Есть открытые вопросы». «Утверждено» ставит пользователь (или явное «утверждаю»). `sa-spec` сам не утверждает и не публикует.

## Критерий готовности `sa-spec`

Работа завершена, когда:

* сформированы все необходимые локальные спецификации (для выбранного режима);
* нет незафиксированных неизвестностей;
* каждый открытый вопрос имеет статус;
* блокирующие вопросы решены;
* решения отражены в соответствующих артефактах;
* self-check пройден;
* сформирован `publish-plan.md`.

Для режимов «разложение» и «только вопросы» критерии уже: карта и/или вопросы с статусами.

Показать пользователю: что написано локально, какие вопросы открыты, что нужно для `sa-publish`. Не вызывать публикацию.

## Ограничения

Нельзя:

- публиковать в Confluence / Git / Jira;
- придумывать продуктовые, архитектурные или контрактные решения;
- выдавать догадку как требование;
- читать весь репозиторий или все фичи «на всякий случай»;
- создавать пустые папки «на будущее»;
- подменять `sa-review` своим чек-листом;
- ставить статус «Утверждено» без явного решения пользователя.
