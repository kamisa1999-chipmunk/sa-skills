# Источники и поэтапная загрузка

Приоритет источников для `sa-spec`:

1. текущая Jira-задача;
2. feature notes;
3. ранее зафиксированные решения;
4. существующая документация Confluence/Git;
5. существующие контракты;
6. аналогичные спецификации;
7. код/proto/OpenAPI/schema — если документации недостаточно или нужно проверить фактическое состояние.

Не читать всё подряд.

## Уровни (как в `sa-review`)

### Уровень 1 — обязательно

- Jira-задача:

```bash
python3 "$JIRA_WRITE_REPO_DIR/scripts/cli/get_issue.py" <ISSUE-KEY>
```

Клиент Jira — из соседнего репозитория [`jira-write`](https://github.com/kamisa1999-chipmunk/jira-write), если нет MCP. Токены не читать и не показывать.

- чек-лист: `skills/sa-review/checklist-close-sa.md` в этом репозитории (читать с диска, не из памяти);
- прямые ссылки из Jira.

Токены не читать и не показывать.

### Уровень 2 — связанные артефакты

Только страницы / спецификации / задачи, которые:

- прямо указаны в задаче;
- явно затронуты изменением;
- нужны, чтобы понять связность (экосистема: версии, потребители, UI, соседние контракты).

Confluence по `pageId`:

```bash
python3 ~/.cursor/skills/sa-review/scripts/dump_confluence_page.py PAGE_ID
```

В `context.md` записать `pageId`, title, **версию на момент загрузки**. Страницу не изменять.

Поиск аналогов / существующей страницы по названию:

```bash
python3 ~/.cursor/skills/sa-spec/scripts/search_confluence.py --title "GetLabels"
python3 ~/.cursor/skills/sa-spec/scripts/search_confluence.py --cql 'space = BIZ AND title ~ "Label"'
```

Не проверять только ту страницу, на которую есть ссылка в задаче, если изменение затрагивает связанные объекты.

### Уровень 3 — контекст фичи

Если в workspace есть feature notes — один релевантный файл. Не читать все файлы фич.

### Уровень 4 — источник конкретного решения

Только при потенциальном противоречии: заметки груминга, история Jira (`jira-history`), комментарий, связанная задача. Не собирать всю историю фичи без нужды.

Код / proto / OpenAPI — уровень 4: только если документ молчит или нужно сверить факт.

## Карта артефактов

Перед генерацией:

```text
что меняется
→ где это должно быть описано
→ существует ли уже такой документ
→ создать или обновить
```

Типы документов сверять с разделом «Спецификации и шаблоны» чек-листа (HTTP, gRPC, Kafka, коллекция/БД, UI, админка, страница фичи). Чек-лист в скилле не дублировать.

Пример:

```text
HTTP GetLabels V3
→ существующая страница отсутствует
→ создать

Product.labels
→ существующая спека есть
→ проверить, требуется ли изменение

ProductLabel_{storeId}
→ существующая спека есть
→ обновить
```

## Аналогичные спецификации

Для каждого **нового** типа документа найти 1–3 релевантных существующих примера (поиск по title / соседние страницы того же родителя / ссылки с канона фичи).

Использовать их для:

* структуры;
* принятого шаблона;
* терминологии;
* обязательных разделов.

Не копировать содержимое аналогов как фактические требования.

Шаблоны Confluence — ссылки в чек-листе. Перед генерацией документа данного типа:

1. Выгрузить актуальную страницу шаблона (`dump_confluence_page.py` + pageId из таблицы ниже).
2. Если выгрузка не удалась — локальный снимок `~/.cursor/skills/sa-spec/templates/` ([README.md](templates/README.md)).
3. Зафиксировать в `context.md`, какой источник шаблона использован (живая версия или снимок с датой).

Не подставлять структуру из памяти. Не выдавать снимок за актуальную Confluence.

Если для типа нет утверждённого шаблона — 1–3 аналога + применимые пункты чек-листа.

## Экосистема

Для изменённого объекта пройти:

```text
метод
→ версии
→ потребители
→ UI
→ связанные контракты
→ документация
```

Если меняется V2: существует ли V1; должен ли остаться неизменным. Не требовать изменение V1 автоматически. Сознательно неизменяемое — явно в `context.md` и в спеке.
