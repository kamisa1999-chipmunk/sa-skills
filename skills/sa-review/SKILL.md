# SA-review

Проверка SA-задачи по чек-листу. Пишет про состояние артефакта, не про автора. Не сочиняет спецификацию. Не публикует в Jira/Confluence без подтверждения.

Ядро (поиск) общее во всех режимах. Режим меняет только presentation layer и, для `lead-review`, шаг истории **после** технического ревью.

Не читать reference-файлы заранее. Каждый — только на своём этапе.

## Источники истины

```text
checklist-close-sa.md
```

Файл рядом с этим `SKILL.md`. Читать целиком на шаге минимального контекста. В скилле чек-лист не дублировать. Jira-копипаст `checklist-close-sa-jira.txt` — вспомогательный. Если в workspace есть более новый канон команды — читать его.

Связка: этот скилл не пишет спеки и не публикует. Комментарий в Jira — только через скилл `jira-write` (репозиторий `jira-write`) после подтверждения. `jira-history` — только уровень 4 в `evidence-and-context.md`.

Jira и Confluence читать так: сначала уже доступный в окружении источник (MCP, connector, встроенный tool); если подходящего нет — локальный fallback из репозитория. Команды `get_issue.py` и `dump_confluence_page.py` не обязательны. Выбор источника, обязательные поля и режимы установки — в `sources.md`.

## Режимы

Определить режим **до** чтения карточки сотрудника. Нет контекста между самопроверкой и ревью → `review`.

| id | Для пользователя | Когда |
|----|------------------|--------|
| `self-check` | Самопроверка | «проверь мою аналитику», «перед ревью», «self-check», «готова ли к ревью», «что я не учла» |
| `review` | Техническое ревью | «сделай ревью», «поревьюй», «найди проблемы», «можно ли отдавать в разработку» |
| `lead-review` | Ревью тимлида | «лид-ревью», «с историей», «повторились ли ошибки», «зафиксируй в карточке» |

`self-check`: карточку не читать; историю ошибок не учитывать; в Jira не писать. Если в workspace есть локальные черновики спек по ключу задачи — проверить их плюс Jira.

`review`: карточку не читать. Правила Jira чужой команды — в `applicability.md` на этапе applicability.

`lead-review`: то же ядро **целиком**. Карточка сотрудника — только после готового технического ревью. История не может влиять на поиск текущих замечаний. Запрещено: «раньше ошибалась → наверное и сейчас». Разрешено: сначала текущий дефект → затем категория уже встречалась.

## Инварианты

- один этап закончен → только потом следующий;
- finding не формировать до проверки evidence;
- scope не менять неявно и не сокращать ради токенов;
- не выдумывать missing context;
- применимость неясна → уточнение / `NEEDS_CLARIFICATION`, не `ISSUE`;
- нет evidence на расхождение → `NEEDS_CLARIFICATION`, не `ISSUE`;
- тип открытой спецификации определить нельзя → `NEEDS_CLARIFICATION`, не `ISSUE`;
- один root cause → один finding;
- независимые проблемы с разными исправлениями или решениями не сливать в один root cause;
- всю очередь findings собрать до первого показа;
- очередь не фиксировать, пока coverage gate не проставлен по всем веткам;
- очередь не фиксировать, пока каждый подтверждённый gap не имеет статуса reconciliation;
- связанная Jira может активировать ветку; `not applicable` только после проверки её содержания;
- «дальше» не запускает повторный анализ;
- при конфликте источников не выбирать правильный без evidence;
- историю сотрудника не использовать для поиска дефектов;
- не публиковать автоматически;
- не читать карточку в `self-check` и обычном `review`.

## Pipeline

Идти строго по порядку. Не показывать пользователю внутреннюю модель.

```text
определить режим
→ собрать минимальный контекст          ← прочитать sources.md
→ построить карту изменения
→ определить applicability          ← прочитать applicability.md
→ собрать и проверить evidence      ← прочитать evidence-and-context.md
→ сформировать полный набор findings
→ сгруппировать и приоритизировать
→ coverage gate                     ← прочитать coverage-gate.md
→ reconciliation                    ← прочитать reconciliation.md
→ назначить категории               ← прочитать error-taxonomy.md
→ показать через presentation layer ← прочитать review-style.md
→ lead-review: история сотрудника   ← карточка + error-taxonomy.md
```

Копировать:

```text
SA-review:
- [ ] Режим (карточка ещё не открыта)
- [ ] Минимальный контекст (sources.md: Jira выбранным источником + чек-лист)
- [ ] Карта изменения
- [ ] Applicability (applicability.md)
- [ ] Evidence (evidence-and-context.md), в т.ч. тип и шаблон каждой открытой спеки
- [ ] Полный набор findings
- [ ] Группировка и приоритет очереди
- [ ] Coverage gate (coverage-gate.md) — все ветки: checked / not applicable / needs clarification
- [ ] Reconciliation (reconciliation.md) — каждый gap: own finding / merged / NEEDS_CLARIFICATION / снят
- [ ] Категории (error-taxonomy.md)
- [ ] Очередь зафиксирована
- [ ] Вывод (review-style.md) — только после ядра
- [ ] (lead-review) карточка после технического ревью
```

### 1. Минимальный контекст

Прочитай `sources.md`. Прочитать Jira-задачу выбранным источником (MCP / connector / tool, иначе local CLI fallback). Прочитать чек-лист с диска. Demo / локальный self-check / уровни 2–4 — в `evidence-and-context.md`, не здесь.

### 2. Карта изменения

Внутренне, не в комментарий:

```text
фича → точки входа → компоненты → контракты → затронутая документация
```

Зафиксировать: цель; платформы; экраны / точки входа; сервисы; методы; версии контрактов; события; БД / коллекции; админки; прочие компоненты.

### 3. Applicability

После карты изменения прочитай `applicability.md` и определи применимые ветки.

### 4. Evidence

Прочитай `evidence-and-context.md`. Собери evidence по применимым веткам. Для каждой открытой спецификации обязательно определить тип и сверить с шаблоном — правило применения раздела 3 чек-листа, не новый пункт. Finding ещё не писать в вывод.

### 5. Findings, группировка, приоритет

Состояние артефакта, не человек. Не писать решение за аналитика. Не комментировать каждый пункт чек-листа. Внутренне: проблема + основание + ожидаемое состояние (внешний текст — в `review-style.md` перед показом).

- один root cause → один смысловой блок;
- не сливать в один блок независимые проблемы, которым нужны разные исправления или решения;
- разделять блоки, если нужны независимые изменения или разные решения;
- очередь ранжировать по влиянию на понимание и реализацию, не по чек-листу; пользовательские severity не вводить.

Полную очередь ещё не фиксировать.

### 6. Coverage gate

Перед фиксацией очереди прочитай `coverage-gate.md`. Пройти все ветки gate и проставить `checked` / `not applicable` / `needs clarification`. Не полный повторный анализ: только поймать случайный пропуск. Связанные Jira сами могут включить ветку; `not applicable` — только после проверки их содержания.

### 7. Reconciliation

Перед фиксацией очереди прочитай `reconciliation.md`. Для каждого подтверждённого gap — один статус: `own finding` / `merged into finding N` / `NEEDS_CLARIFICATION` / снят. Пользователю не показывать. Нельзя терять gap из‑за группировки в более крупный finding. Независимые проблемы с разными исправлениями не считать одним root cause.

### 8. Категории

Когда findings уже сформированы, coverage gate и reconciliation пройдены, прочитай `error-taxonomy.md`. Назначить категорию, чтобы классифицировать, не чтобы «найти» проблему. Таксономию не расширять. Одна основная категория на внешний блок.

Низкая уверенность → как правило `NEEDS_CLARIFICATION`, не `ISSUE`.

Очередь зафиксировать. После этого не искать новые дефекты.

### 9. Вывод

Перед первым сообщением пользователю прочитай `review-style.md`. Ядро к этому моменту завершено.

«дальше» / «следующий» / «покажи всё» — только показ готовых блоков.

### 10. Lead-review: карточка

Только после готового технического ревью. Если в workspace есть карточка сотрудника — сравнить категории с уже записанными блоками и предложить запись после подтверждения. Формат секции — в `error-taxonomy.md`. Если карточки нет — техническое ревью всё равно полное; историю повторов между задачами не выдумывать. Историю не использовать для поиска новых дефектов.

## Запреты

Нельзя: автоматически менять Jira или Confluence; придумывать спецификацию; читать весь репозиторий без нужды; дублировать чек-лист; писать runtime-state в tracked-файлы; перечитывать артефакты на «дальше».
