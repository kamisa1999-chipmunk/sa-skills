# Evidence и контекст SA-review

Читать **после** applicability, когда собираешь и проверяешь evidence. Не читать в начале прогона. Не формировать finding до этой проверки.

Чек-лист: `checklist-close-sa.md` рядом с `SKILL.md` (уже прочитан на минимальном контексте). Jira-копипаст `checklist-close-sa-jira.txt` — только вспомогательный.

Не читать репозиторий «на всякий случай». Полнота ревью не зависит от экономии токенов: нельзя сузить scope, пропустить артефакт из карты или заменить `ISSUE` на `NEEDS_CLARIFICATION` только чтобы сэкономить контекст.

## Минимальный контекст (уровень 1)

Уже должен быть собран до applicability: Jira-задача, чек-лист, прямые ссылки из Jira (открывать по правилам уровней ниже, не все подряд).

Из Jira (любым выбранным источником): summary, description, type, links, parent/epic при необходимости, комментарии про аналитику и прошлые ревью. Сразу свернуть в evidence summary. Повторно не читать ту же задачу, пока она не изменилась и для уровня 4 не нужна история. Как выбирать источник — уже в `sources.md`; здесь не переключать.

Связанные Development/Testing и прочие связанные задачи: если уже заведены, их links/type/component/summary могут активировать ветку applicability (analytics, iOS/Android, admin и т.п.) — такие задачи нужно прочитать, не только когда проверяется качество Jira. Не читать весь проект. Не читать историю Jira, пока уровень 4 не нужен.

Токены не читать и не показывать.

Если пользователь просит самопроверку **локальных** артефактов и в workspace есть черновики спек по ключу задачи — предмет проверки: эти файлы плюс Jira. Результат записать рядом, если пользователь просила сохранить self-check. Confluence читать, если локальный черновик ссылается на существующую страницу (сверка, не публикация).

### Демо-режим (не меняет критерии ревью)

Если ключ `DEMO-XXX` или в workspace есть дерево `sa-demo/`:

- Jira = локальный файл кейса (не live Jira);
- спеки = локальные черновики кейса;
- **не читать** oracle/`expected/` — это для человека;
- не писать в Jira и не открывать карточки сотрудников;
- чек-лист с диска применять только по релевантным пунктам качества артефакта.

Если такого дерева нет — демо-режим не включать.

## Уровень 2 — связанные артефакты

Открывать только страницы / спецификации / задачи, которые:

- прямо указаны в задаче;
- явно затронуты изменением;
- связаны в Jira и по type / component / labels / summary могут активировать ветку applicability (analytics, iOS/Android, admin и т.п.);
- нужны для проверки связности (экосистема) **конкретного применимого критерия**.

Связанные страницы открывать только когда они нужны для проверки конкретного критерия или finding. Не обходить все ссылки подряд.

Confluence читать выбранным источником из `sources.md` (MCP / connector / tool, иначе local CLI fallback). Нужны: title, URL, актуальное содержимое; version / date и labels / тип страницы — при наличии. Токен не читать. Страницу не изменять. После чтения — evidence summary; повторно не выгружать ту же страницу в том же прогоне, если версия не изменилась. Если источник не отдал обязательные поля — точечно добрать или `NEEDS_CLARIFICATION`, не считать страницу проверенной.

Не проверять только ту страницу, на которую аналитик дал ссылку, если изменение затрагивает связанные объекты.

Если текущая Confluence-страница явно ссылается на соседнюю спецификацию как на источник поля, модели, алгоритма, UI-правил, контракта или поведения — открыть её до фиксации finding. Не считать информацию отсутствующей, пока не проверена явно указанная связанная страница. Не обходить все ссылки подряд, только релевантные текущему критерию. Явно делегированную туда информацию проверять до фиксации `ISSUE`.

## Уровень 3 — контекст фичи

Если в workspace есть заметки по фиче и они нужны, чтобы понять принятые решения или область изменения — один релевантный файл. Не читать все файлы фич. Если таких заметок нет — уровень пропустить.

## Уровень 4 — источник конкретного решения

Только при потенциальном противоречии: заметки груминга, история Jira, комментарий, связанная задача, сохранённый контекст обсуждения. Не собирать всю историю фичи без нужды. Тогда читать историю выбранным источником (`jira-history` или другой доступный tool; иначе local CLI fallback из `sources.md`).

## Evidence summary и повторное чтение

Каждый Jira/Confluence-артефакт (и локальную спецификацию в self-check) читать один раз за прогон, если он не изменился.

Повторно открывать только если:

- версия / дата обновления не совпадает с summary;
- пользователь сказала, что артефакт обновился;
- для применимого критерия в summary нет факта, без которого нельзя вынести тот же статус, что при полном тексте.

Не перечитывать Jira/Confluence на каждый finding и не на команду «дальше». Не вызывать local CLI fallback, если артефакт уже есть в summary.

Если компактного summary не хватает, чтобы подтвердить или опровергнуть применимый критерий — перечитать **этот** артефакт и обновить summary. Не ставить «Требует уточнения» из‑за обрезанного кэша.

Сразу после чтения держать внутренний компактный summary (пользователю не показывать как лог):

```text
ссылка
тип — jira / confluence / local spec / feature note
тип спецификации — HTTP / gRPC / UI / Admin / DB / Kafka / feature page / другое / не определён
версия или дата
ключевые факты
сущности — методы, поля, версии, экраны, компоненты
потенциальные противоречия
```

На следующих шагах опираться на summary, а не заново грузить полный текст. Полный текст нужен, чтобы построить summary, а не чтобы таскать его через всю очередь.

## Runtime-state

Временное состояние прогона — только в памяти сессии и в неотслеживаемых dump.

Нельзя писать evidence summary, карту изменения, очередь findings, coverage gate, reconciliation или сырые выгрузки в tracked-файлы скилла.

Dump Confluence/Jira — только во временную папку / `reports/` (не в git). После прогона удалить файлы, созданные в этом запуске. Не коммитить их.

## Проверка evidence

`applicable` / `NOT_APPLICABLE` уже определены матрицей **до** поиска evidence. Дальше проверять только включённые ветки и соответствующие пункты чек-листа.

Для каждой открытой Confluence-страницы и каждой локальной спеки в self-check сначала выполнить правило типа и шаблона ниже. Это применение раздела 3 чек-листа, не новый критерий и не отдельная ветка матрицы.

### Тип и шаблон каждой открытой спецификации

Закрытый набор типов: `HTTP` / `gRPC` / `UI` / `Admin` / `DB` / `Kafka` / `feature page` / `другое`.

Не вспоминать структуру шаблона «как обычно». Карта тип → утверждённый шаблон — в уже прочитанном `checklist-close-sa.md` (раздел «Спецификации и шаблоны»). Саму карту в этот файл не копировать.

#### 1. Определить тип

Опереться на все доступные сигналы, не на один:

1. **Заявленный тип:** labels (`http`, `grpc`, `ui-component`, `adminapp`, `topic`, `collection`, `feature`); заголовок; родитель / раздел; указание «создано из шаблона …»; для локальной спеки — каталог `specs/http/`, `specs/grpc/` и т.п.
2. **Структура:** набор разделов, совпадающий с известным шаблоном.
3. **Содержимое объекта спецификации:** что страница на самом деле описывает как свой контракт / объект (REST-путь и HTTP-метод; proto / rpc / `Service.Method`; UI-экран; админка; коллекция / БД; топик; обзор фичи).

Расхождение заявленного типа и содержимого — это не «тип неизвестен», а кейс проверки содержимого (шаг 3). Пример, который должен стабильно ловиться: страница размечена как HTTP (label, `GET/POST` + URL, Swagger), а по содержанию специфицирует gRPC (proto, rpc, метод сервиса). Обратное — тоже.

Тип `другое` — определённый вывод: для страницы нет шаблона из списка чек-листа. Это не «не определён».

Тип не определён, только если нет надёжного основания выбрать один тип из набора. Тогда `NEEDS_CLARIFICATION`, не `ISSUE`: спросить, какого типа эта страница должна быть. Не угадывать шаблон и не ставить замечание за несоответствие угаданному шаблону.

#### 2. Сверить тип и структуру с шаблоном

Для `HTTP` / `gRPC` / `UI` / `Admin` / `DB` / `Kafka` / `feature page`: взять соответствующий шаблон из чек-листа. Выгрузить эту страницу шаблона выбранным источником Confluence, если её ещё нет в summary этого прогона. Если выгрузка не удалась — локальный снимок `templates/` рядом с этим файлом. Не выгружать шаблоны типов, которые в этом прогоне не открывались.

Проверить:

- страница данного типа использует шаблон этого типа, а не шаблон другого;
- обязательные разделы шаблона заполнены либо помечены «не применимо» с причиной (формулировка — в чек-листе, здесь не дублировать).

Для `другое`: не навязывать шаблон из списка; полноту смотреть по аналогам, как в том же разделе чек-листа. Если аналог неясен — `NEEDS_CLARIFICATION`.

Особый случай админки из чек-листа: методы админки — отдельные HTTP-страницы со ссылками из документации админки. Полное описание HTTP-метода на странице админки вместо HTTP-спеки — расхождение типа/шаблона, не «так и должно быть, потому что это админка».

#### 3. Содержимое vs заявленный тип

Отдельная проверка, не замена сверки структуры. Даже если разделы похожи на нужный шаблон, описываемый объект должен соответствовать типу страницы.

Отличать от уже существующих кейсов:

- неверный тип страницы или содержимое противоречит заявленному типу — это правило;
- тип страницы верный, но в алгоритме смешаны уровни другого контракта (например SDK-поля на gRPC-странице) — существующее смешение уровней, не подменять им проверку типа;
- легитимные ссылки на спецификации другого типа — не дефект типа.

Если шаблон выгрузить не удалось и снимка нет: структурную сверку пометить как `NEEDS_CLARIFICATION`, проверку содержимого vs типа всё равно выполнить.

#### Вердикт этой проверки

| Ситуация | Вердикт |
| --- | --- |
| Тип определён, структура и/или содержимое ему противоречат | `ISSUE` |
| Тип страницы определить нельзя | `NEEDS_CLARIFICATION` |
| Тип `другое`, аналог или достаточность описания неясны | `NEEDS_CLARIFICATION` |
| Тип, шаблон и содержимое согласованы | дальше остальные применимые критерии |

Новую категорию не заводить. Когда finding уже сформулирован, типичные категории — актуальность документации или смешение уровней контрактов.

### Модель проверки evidence

Внутренняя модель (не показывать эти ключи пользователю):

```text
criterion — проверяемый критерий
applicable — применим ли критерий к текущей задаче
expected_state — ожидаемое состояние артефакта
evidence — основание для вывода
verdict — результат проверки
gap — найденное расхождение
confidence — уверенность в выводе
```

Подтверждённые gap (`ISSUE` или `NEEDS_CLARIFICATION`) копить внутренним списком до шага `reconciliation.md`. Не заменять этот список уже сгруппированной очередью.

### Результаты проверки

| Технический статус | Русское название | Что означает |
| --- | --- | --- |
| `OK` | Выполнено | Критерий применим и подтверждён найденными артефактами |
| `ISSUE` | Есть замечание | Найдено конкретное расхождение с критерием |
| `NEEDS_CLARIFICATION` | Требует уточнения | Данных недостаточно, чтобы достоверно подтвердить или опровергнуть выполнение |
| `NOT_APPLICABLE` | Не относится | Критерий неприменим к текущей задаче |

> Отсутствие найденного основания не означает автоматически «есть замечание». Не выдумывать missing context.

Если состояние нельзя достоверно установить — «Требует уточнения» (`NEEDS_CLARIFICATION`), не `ISSUE`.

Пункт чек-листа «не относится» без причины не считается заполненным (это в самом чек-листе).

Не считать началом разработки доказательством качества аналитики. Не считать отсутствие вопросов от разработчиков доказательством полноты.

## ISSUE vs NEEDS_CLARIFICATION и неизвестный контекст решений

Различать три ситуации. Не превращать вопрос про решение в `ISSUE` только потому, что причина не написана.

1. **Есть подтверждённое расхождение**  
   Ставить `ISSUE`, если по доступным артефактам видно конкретное несоответствие применимому критерию: противоречие, отсутствие обязательной информации, несогласованность спецификаций и т.п. Сюда же: страница заявленного типа описывает объект другого типа (например размечена как HTTP, а специфицирует gRPC). Если тип страницы определить нельзя — не этот случай, а `NEEDS_CLARIFICATION` по правилу типа и шаблона выше.

2. **Не хватает контекста принятого решения**  
   Если техническое поведение описано, но непонятно, почему выбрано именно оно или сознательно ли исключён какой-то компонент / версия / платформа:
   - не считать это автоматически ошибкой;
   - сформулировать короткий вопрос аналитику или ревьюеру;
   - использовать `NEEDS_CLARIFICATION`, если без ответа нельзя понять корректность решения.

   Примеры вопросов:

   ```text
   Правильно ли понимаю, что V1 сознательно остаётся без изменений?
   Для mobile этот сценарий не меняется по принятому решению?
   Есть отдельное решение, почему здесь используется именно такое поведение для null?
   ```

3. **Есть решение, но оно не зафиксировано там, где должно жить**  
   Если после ответа становится понятно, что решение существует, но его нет в актуальной спецификации, это уже может быть `ISSUE` категории фиксации решений / непротиворечивости документации (`decision-traceability` / связанные категории). Файл категорий читать только после формирования findings.

Конфликт источников:

- не выбирать правильный источник наугад и не выбирать «правильный» без evidence;
- если Jira, Confluence или другие артефакты расходятся — фиксировать противоречие и запрашивать уточнение;
- комментарий в Jira не считается достаточной заменой спецификации, если решение необходимо для реализации или сопровождения и должно жить в документации;
- более новый явно зафиксированный источник имеет приоритет над старым, но только если из контекста понятно, что он действительно заменяет прежнее решение.

Для `review` чужой аналитики вопросы — нормальный результат ревью и не должны искусственно превращаться в замечания.

## Экосистема изменения

Для изменённого объекта пройти связанные части:

```text
метод
→ версии
→ потребители
→ UI
→ связанные контракты
→ документация
```

Если меняется V2: существует ли V1; должен ли остаться неизменным; если да — это должно быть однозначно в аналитике. Не требовать изменение V1 автоматически.

То же: несколько платформ; несколько экранов; backend + frontend; BFF + SDK; HTTP + gRPC; producer + consumer.

## Решения

Если решение влияет на архитектуру, контракт, пользовательское поведение, надёжность, способ реализации или область изменения, проверить:

1. отражено ли само решение;
2. понятна ли причина, если она нужна дальше;
3. нет ли более нового решения, которое его заменило.

Если документация расходится с ранее согласованным решением, не считать автоматически одну сторону правильной и не выбирать источник наугад. Сначала зафиксировать противоречие и уточнить, какой источник актуален. Формулировка, когда расхождение уже видно:

```text
текущее описание расходится с ранее зафиксированным решением;
нужно либо привести артефакт к актуальному решению,
либо зафиксировать, что решение было пересмотрено.
```

Основание (даты груминга, цитаты) — во внутреннем finding; в Jira-комментарий не класть автоматически.

## Замечания предыдущего ревью

Если задача уже была на ревью: сначала сверить все содержательные замечания прошлой итерации, затем выполнить полноценное ревью текущего состояния и искать новые проблемы.

Не дублировать одно и то же замечание одновременно как старое незакрытое и новое `ISSUE`.

1. **Предыдущее замечание закрыто**  
   Если артефакт изменён или принятое решение корректно зафиксировано — не повторять замечание.

2. **Предыдущее замечание не закрыто**  
   Не создавать новое `ISSUE` той же сути. Отмечать как незакрытое замечание предыдущего ревью (`unresolved_previous_review` / `unresolved_previous_comment`). Идентификаторы категорий — после формирования findings.

3. **После исправления появился новый дефект**  
   Если проблема действительно другая по смыслу и требует отдельного решения — считать новым finding, даже если она находится в том же документе или разделе.

4. **Формально ответили, но артефакт не исправили**  
   Ответ в Jira или комментарии сам по себе не закрывает замечание, если информация должна быть отражена в спецификации. Недостаточно: написать «сделано»; объяснить решение только в комментарии, если оно должно жить в документации.

5. **Область задачи изменилась**  
   Если старое замечание стало неприменимо из-за изменения scope, считать его закрытым с причиной, а не незакрытым.
