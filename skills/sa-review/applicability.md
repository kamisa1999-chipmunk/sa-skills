# Применимость критериев SA-review

Читать **после** карты изменения и **до** сбора evidence. Не читать в начале прогона.

Внутренняя логика. Не новый чек-лист и не пользовательский вывод. Не выводить матрицу по умолчанию.

После карты изменения и до проверки чек-листа по пунктам: для каждой ветки ниже определить `applicable` / `not applicable`. Искать evidence только у применимых веток. Формулировки полного чек-листа не дублировать — матрица только включает или выключает ветки проверки.

## Правила

- нельзя сначала не найти артефакт, а потом объявить критерий применимым только ради замечания;
- если применимость сама неясна — это не `ISSUE`: сначала уточнить область изменения или поставить `NEEDS_CLARIFICATION`;
- отсутствие клиентской части, админки, схемы, события и т.п. само по себе не делает ветку применимой;
- не менять карту изменения неявно, чтобы включить или выключить ветку;
- критерий шаблонов (раздел 3 чек-листа) применяется к каждой реально затронутой открытой спецификации, даже если ветка «Контракт / метод / API» выключена. Это не новая ветка матрицы и не новый чек-лист; как проверять тип и шаблон — в `evidence-and-context.md`;
- связанные, дочерние и реализующие Jira-задачи сами могут сделать ветку applicable: смотреть type, component, labels, summary, description (analytics / events, iOS / Android / Web, admin, Kafka, БД и т.п.). Не ставить `not applicable` только потому, что в описании SA эта область не названа;
- если такие задачи есть, их содержание нужно проверить, прежде чем выключать ветку. Перед фиксацией очереди — `coverage-gate.md`.

## Jira чужой команды

В обычном `review` чужой команды не применять локальные правила оформления Jira как универсальный стандарт. Jira использовать как источник scope, связей, статусов и ссылок. `jira-task-quality` использовать только если содержимое Jira реально мешает понять требования или область изменения.

## Scope связанных компонентов

Проверять только объекты, без изменения которых заявленное поведение нельзя реализовать или однозначно понять. Не требовать изменение компонента только потому, что он технически существует.

## Матрица применимости

1. **Клиентские экраны / точки входа**  
   Если изменение влияет на UI, пользовательский сценарий или клиентскую точку входа: все затронутые точки входа; сценарий «действие → реакция системы → результат»; различия Web / iOS / Android и других платформ, если они возможны. Нет клиентской части — ветка неприменима.

2. **Несколько компонентов / систем**  
   Если участвуют два и более компонента или системы: наличие и достаточность схемы взаимодействия; последовательность вызовов и границы ответственности. Если изменение локально внутри одного компонента и взаимодействие не меняется — схема может быть неприменима.

3. **Контракт / метод / API**  
   Если создаётся или меняется HTTP, gRPC, SDK или другой контракт: обязательность новых и изменённых полей; поведение для отсутствующего поля / `null` / пустого значения, если такие состояния возможны; связанные методы и потребители; соответствие документации типу контракта; в одной спецификации не смешаны разные уровни контрактов. Тип и шаблон самой страницы проверять по правилу в `evidence-and-context.md`, не только в этой ветке.

4. **Версии контрактов**  
   Если есть несколько версий метода / контракта или создаётся новая версия: область применения каждой версии; какие потребители используют каждую; должна ли старая версия сохранить прежнее поведение. Не требовать изменение старой версии автоматически, если это не следует из области задачи.

5. **Данные / БД / коллекции**  
   Если затрагивается хранение или структура данных: новые и изменённые поля; обязательность и допустимые состояния; правила чтения / записи / преобразования; влияние на связанные контракты и компоненты. Структура и обработка данных не меняются — ветка неприменима.

6. **События / аналитика / Kafka**  
   Если создаётся или меняется событие: условие отправки / публикации; набор полей; источник значения каждого поля; producer / consumer и связанные контракты; альтернативные сценарии, если событие может не отправляться или обрабатываться по-разному.

7. **Админка**  
   Если затрагивается административный интерфейс: UI админки; связанные backend-методы; правила отображения / редактирования / валидации; ссылки между документацией админки и методами. Админка не участвует — ветка неприменима.

8. **Связанные компоненты и экосистема**  
   Для любого нового или изменённого поля, правила, метода или сценария: связанные UI, методы, версии, потребители и документация. Scope — раздел «Scope связанных компонентов» выше.

9. **Альтернативные и ошибочные сценарии**  
   Edge cases только если они возможны для текущего изменения: отсутствие данных; пустой ответ; недоступность зависимости; конфликт данных; другие реально применимые состояния. Не генерировать абстрактные edge cases без основания в архитектуре или контракте.

10. **Принятые решения**  
    Если в Jira, Confluence, комментариях или связанных материалах есть решение, влияющее на архитектуру, контракт, поведение, надёжность или область изменения: отражено ли в актуальной документации; нет ли противоречия с более новым решением. Причину требовать только там, где она нужна для дальнейшего понимания.

11. **Jira development / testing tasks**  
    Качество задач разработки и тестирования — только если они уже существуют или по процессу должны быть заведены на текущем этапе: релевантные ссылки; понятная область изменения; различия по платформам; достаточность требований для реализации / проверки. Не считать отсутствующую downstream-задачу дефектом, если её ещё не должны были заводить. Для чужой команды — также раздел «Jira чужой команды».

12. **Общие критерии качества**  
    Для каждой реально затронутой спецификации всегда: однозначность; непротиворечивость; актуальность; проверяемость; выполнимость; отсутствие незакрытых placeholders и незафиксированных решений.

Перед фиксацией очереди findings — короткий coverage gate в `coverage-gate.md`. Он не добавляет строки в эту матрицу и не заменяет её.
