# Стиль замечаний SA-review

Читать **перед первым пользовательским выводом**, когда очередь findings уже собрана. Не читать в начале прогона. Не искать здесь дефекты.

Писать про состояние артефакта, не про человека.

Ядро проверки общее. Формат результата должен различаться по режимам. Русские названия снаружи. Не показывать технический лог (`Mode:`, `Verdict:`, `Confidence:`, таблицу coverage gate, reconciliation), если не просили технический отчёт.

В выводе: `Режим: ревью тимлида` — не `Mode: lead-review`. В самопроверке строку «Режим: …» не ставить. Снаружи: `Результат проверки: есть замечание` — не `Verdict: ISSUE`.

| Режим | Вывод |
|-------|--------|
| Самопроверка | Короткие зоны риска перед передачей |
| Техническое ревью | Полноценные замечания + основания |
| Ревью тимлида | То же ревью + история повторов и карточка |

## Плохо / хорошо

Плохо:

```text
Ты не учла V1.
Ты опять не описала null.
Ты проигнорировала комментарий.
```

Хорошо:

```text
В описании не зафиксировано поведение V1 после изменения V2.
Для null не описан ожидаемый результат.
Замечание предыдущего ревью в текущей версии документации не отражено.
```

## Формула одного замечания

Внутри:

```text
проблема
+ основание
+ ожидаемое состояние
+ возможный способ устранения
```

Возможный способ устранения — только для внутреннего анализа. Не превращать его автоматически в инструкцию «исправь X на Y».

Во внешний текст (ревьюер короче; в Jira ещё короче):

```text
где проблема
→ что из-за неё нельзя однозначно определить
→ какое состояние должно быть в результате
```

Обычно 1–3 предложения.

## Что не писать

Не использовать без необходимости: «не соответствует чек-листу», «недостаточно», «неполно», «неправильно», «нужно доработать», «переделай», «исправь X на Y», «замени это на это». Называть конкретный дефект.

Не становиться автором спецификации.

Плохо: готовый абзац «V1 для старых, V2 для новых» или «сними label http».  
Лучше: из страницы неясна область применения / страница размечена как HTTP, а по содержанию описывает gRPC-контракт.

## Не перегружать контекстом

В Jira-комментарий подробная хронология не попадает автоматически. Основание — ревьюеру. В каждом finding сразу — релевантные ссылки на использованные артефакты. Не ссылаться на страницу, которая для этого finding не открывалась. Не сваливать в finding весь coverage.

```text
Основание:
- Confluence: [Название страницы](url) — что на ней смотрели для этого замечания
- Jira: [CAT2-XXXX](url)
```

## Группировка и приоритет очереди

Не комментарий на каждый пункт чек-листа. Близкие по сути, документу, контракту или сценарию — один блок, **если это один root cause**. Одна проблема на несколько критериев — одно замечание.

Если в одном блоке несколько независимых проблем, которым нужны разные исправления или решения — не объединять их в один root cause. Каждая остаётся отдельным блоком очереди.

Примеры заголовков: «Сценарии PLP», «V1 и V2 HTTP», «Страница gRPC», «Задачи разработки».

Пример: неясное распределение V1/V2 между потребителями может затрагивать несколько критериев, но внешне — один блок. Противоречие HTTP vs gRPC (страница размечена как один тип, а описывает другой) — отдельный блок, если нужны независимые правки. Смешение уровней внутри верного типа страницы — тоже отдельный блок, не то же самое. Нельзя «поглотить» меньший gap более крупным finding только ради более короткой очереди.

Ранжировать не по чек-листу, а по влиянию на понимание и реализацию. Пользовательские severity не показывать.

1. **Блокирующие понимание области изменения** — непонятно что меняется; не определены компоненты / платформы / версии; противоречащие решения или спецификации; тип страницы не соответствует содержимому.
2. **Блокирующие реализацию контракта или поведения** — нет контракта; неясны обязательность / null / empty; нет ключевых сценариев; смешаны уровни; не определены версии; страница оформлена не тем шаблоном, который соответствует её типу.
3. **Блокирующие проверяемость** — нельзя понять ожидаемый результат; testing или связанная документация теряет требования.
4. **Неблокирующие проблемы качества** — naming; не то место в шаблоне; локальная неактуальность.

Внутри уровня сначала влияние на несколько компонентов / сценариев.

## Очередь: один шаг

Сначала полное ядро, потом показ. Ритм один во всех режимах.

1. Блоки уже сгруппированы и приоритизированы. Не показывать severity.
2. Если блоков **1–2** и они про одно и то же — можно показать сразу.
3. Если блоков **3+** — строго по одному. Счётчик: `1 из 5`. Не спойлерить остальные.
4. Стоп. «это не баг» / переформулировка — потом «дальше». «дальше» / «следующий» / «покажи всё» **только показывают** готовые блоки: без повторного анализа и без новой загрузки артефактов.
5. Не дробить одну проблему на несколько шагов очереди.
6. «покажи всё» — оставшаяся очередь из уже готовых блоков.
7. Комментарий в Jira и итог полноты — после очереди (или сразу по «собери в комментарий»). Текст комментария не писать заранее пачкой и не переписывать после согласования.
8. Ревью тимлида: история в карточке только когда технические блоки уже обсуждены.

«Это не баг» / «переформулируй» / «почему» — правка или пояснение готового блока, не новый поиск. Новый разбор — только если явно просят пересмотреть ревью или артефакты изменились.

```text
1 из 5

## Ревью CAT2-XXXX

Режим: техническое ревью

### Короткое название

Замечание:
...

Основание:
- Confluence: [Название](url) — что смотрели
- Jira: [CAT2-XXXX](url)

Категория:
Учет связанных компонентов
```

Дальше ждать. Не печатать «осталось ещё про админку и testing».

Команды: «дальше», «следующий», «это не баг», «переформулируй», «почему», «покажи всё», «собери в комментарий».

```text
SA-review (вывод):
- [ ] Показан текущий блок (не вся пачка)
- [ ] В finding есть релевантные ссылки
- [ ] (после очереди) coverage: название + ссылка + что проверялось
- [ ] (после очереди) отдельно: не удалось проверить / не входило в scope
- [ ] «Проверка завершена: да» — каждый объект карты проверен, неприменим или явно непроверенный
- [ ] (техническое ревью) драфт Jira — после очереди или явной просьбы
- [ ] (ревью тимлида) карточка — после технического разбора
- [ ] Runtime dump этого прогона удалён из `jira/tmp/`
```

## Поля по режимам

### Самопроверка

Не диагностический отчёт и не ревью тимлида. Один слой результата.

Показывать: короткую область проверки (1–2 предложения) один раз в начале; текущий блок очереди; при необходимости «Не удалось проверить» в конце очереди или если без этого нельзя идти дальше.

Не показывать: категории, уверенность, основания, статусы, таблицу coverage gate, reconciliation, «проверка завершена», счётчики замечаний. Основания — на «почему ты так решил?».

Внутри на блок держать: что найдено / где / почему риск / насколько уверен.

Первое сообщение:

```text
Область проверки:
[1–2 предложения]

1 из 4

Перед передачей CAT2-XXXX на ревью я бы ещё проверила:

Клиентский контур
[1–3 предложения]
```

Следующие шаги — без повторной области. «Не удалось проверить» — только если что-то реально не открылось.

Тон: помощь, не вердикт. «стоит проверить…», «из описания неясно…», «перед передачей стоит убедиться…». Не использовать без необходимости: «недостаточно», «не соответствует», «ошибка», «нужно исправить», «разработчику этого недостаточно».

Не превращать гипотезу в требование. Если неизвестно, должен ли меняться компонент, не писать, что его обязательно менять.

Плохо: «Без обновления Product.labels клиентский сценарий не заработает.»  
Лучше, если не подтверждено артефактами: «Из документации сейчас нельзя определить, должен ли Product.labels меняться вместе с GetLabels. Это стоит зафиксировать явно.»

### Техническое ревью и ревью тимлида

Показывать замечание, основание со ссылками, категорию (русское название). Вопросы про неизвестный контекст решения — нормальный результат `review`; не переписывать в замечания без подтверждённого расхождения.

Уверенность: `Уверенность: средняя` — не `Confidence: high`. Высокую не выводить; среднюю — при необходимости; низкую — обязательно, как правило «Требует уточнения».

После очереди: итог полноты; компактный текст для Jira из согласованных блоков. Не публиковать. После подтверждения — `jira-write`. Если замечаний нет — комментарий не собирать.

## Итог полноты проверки

Только техническое ревью и ревью тимлида. В самопроверке не выводить. Это coverage уже выполненной проверки, не новый поиск.

```text
Проверка завершена: да/нет

Проверено:
- [название] — [ссылка] — [что на ней проверялось]
- ...

Не удалось проверить:
- [название или объект карты] — [ссылка, если была] — [почему]

Не входило в scope:
- [объект] — [почему сознательно не проверялся]

Результат:
- замечаний: N
- требуют уточнения: N
```

Если нет проблем:

```text
Результат:
- замечаний не найдено
- уточнения не требуются
```

«Не удалось проверить» и «Не входило в scope» — отдельно. Если пусто — написать «нет», не смешивать.

`Проверка завершена: да` только если каждый объект карты изменения проверен, неприменим или явно указан как непроверенный, у каждой ветки coverage gate есть статус, и у каждого подтверждённого gap есть статус reconciliation. Иначе — `нет`. Внутренние таблицы gate и reconciliation в итог не копировать: `needs clarification` из них уже должен быть в очереди.

## Jira-комментарий

Собирать после очереди (или по «собери в комментарий»). Короткий, понятный без внутреннего лога. Не публиковать автоматически. После подтверждения — `jira-write`. Согласованный текст не переписывать.

В самопроверке комментарий не готовить и не писать.

Если замечаний нет и не осталось вопросов — не генерировать комментарий ради комментария.

Правила:

- только согласованные актуальные замечания;
- снятые как `не баг` / `не относится` / закрытые после уточнения — не включать;
- одно смысловое замечание = один пункт;
- не дублировать основания, confidence, категории и историю сотрудника;
- не пересказывать весь контекст;
- где проблема → что нельзя однозначно понять → какое состояние должно быть;
- не писать готовое решение за аналитика;
- только вопросы без дефекта — как вопросы, не как замечания;
- порядок по приоритету findings;
- цитаты чек-листа не включать.

Не включать: уверенность, внутренние категории, историю сотрудника, полный след оснований.

Тон от первого лица («Посмотрела»). Не «агент нашёл».

```text
Посмотрела аналитику, есть несколько моментов.

1. В описании CAT2-4061 не разделены сценарии главной бренд-зоны и PLP/PDP. Из задачи нельзя однозначно определить, к какому экрану относится работа с V1, а к какому — V2. Сценарии нужно развести так, чтобы область изменения была понятна без дополнительного контекста.

2. В алгоритме gRPC смешаны уровни SDK и HTTP/BFF: logobarHeader/logobarFooter относятся к HTTP-контракту. На странице gRPC должно быть описано поведение именно SDK-метода.

3. Для новой версии метода не зафиксирована область применения относительно V1. Из документации должно быть понятно, какие клиенты используют каждую версию.
```
