Оглавление

1. Краткое описание
Что это за компонент, где используется, зачем нужен. Кратко и простыми словами. Необходимо, чтобы при открытии спецификации человек сразу понимал, о чем речь.
Пример: “Бейдж бонусов — маленькая иконка рядом с ценой товара. Показывает количество бонусов. По клику открывается шторка с деталями по начисленным бонусам.”
2. Внешний вид
Прикладываются 1-2 макета или скриншота, чтобы было понятно, о чем идет речь. Если компонент на изображении с другими компонентами, рекомендуется выделить его на изображении.
Если спецификация пишется до задачи на разработку и есть дизайн, перед изображением обязательно прикладывается ссылка на фигму с макетами для конкретной платформы.
Для внешнего вида на Desktop/Tablet/Mobile или IOs / Android достаточно приложить ссылки на макеты из фигмы по каждой платформе.

3. Источник данных / Вызываемое API
У казываем, из какого API / сервиса приходят данные. Если несколько — перечислить все. Структура:
Метод: (ссылка на спецификацию со связью)
Заголовки:   BFF: BaseHeaders (если в методе другие заголовки, то допустимо убрать ссылку и приложить описание)
Основные поля: (поля запроса или ответа метода, которые влияют на компонент. Желательно – со ссылкой на описание атрибутов бэка (через якорь или ссылку на конкретную часть страницы), в котором указано, какие из атрибутов будут в ответе обязательно, какие могут быть пустыми и т.п. Если приложить ссылку затруднительно, то описать в этом пункте текстом)
Ссылка на swagger: (если метод реализован на момент написания спецификации, то swagger приоритетнее примеров запроса / ответа)
Параметры / тело запроса: (необходимо, чтобы front-разработчик мог осуществить вызов метода)
Пример запроса true true
Пример ответа: (если ответ в методе объемный, а для компонента нужна только часть / есть разные варианты ответа – можно указать только ту часть ответа, которая относится к компоненту)
Пример ответа true true

4. Маппинг данных

Примечание: при получении данных из веблейта ключи должны быть добавлены после разработки.

6. Взаимодействие
Что может сделать пользователь с конкретным компонентом: клик, тап, свайп и т.д. Что в этот момент происходит в системе. Если есть аналитические события ИЛИ вызов каких-то методов, например, при нажатии на кнопку — указать со ссылкой на связанную спецификацию.
