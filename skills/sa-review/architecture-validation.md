# Архитектурный анализ перед ревью документации

Читать **только после явного «да»** на вопрос в `SKILL.md`. При «нет» этот файл не открывать и шаги ниже не выполнять.

Этап независим от checklist-ревью. Он не заменяет проверку полноты, непротиворечивости, требований и остальные checklist-проверки. После этого файла — обычный pipeline `SKILL.md`.

Не проектировать альтернативу целиком. Не достраивать неизвестную архитектуру. Отсутствие доказательств — не доказательство корректности.

## Источники

Jira и Confluence — тем же правилом, что `sources.md` (MCP / connector / tool, иначе local CLI). Для этого этапа из Jira нужны описание, требования, acceptance criteria, комментарии, связи и зависимости. Из Confluence — документация аналитика, связанные страницы, процессы, архитектурные и интеграционные документы, ранее принятые решения.

GitLab API — актуальное состояние репозитория, ветки, коммиты, default branch, сверка локальной копии. Дополнительный поиск — только если текущая интеграция его уже умеет.

Локальные git-репозитории — фактическая реализация. На машине есть репозитории кластера, не вся компания. Нет репозитория — ограничение данных, не подтверждение, что реализации нет.

Приоритет current state:

1. код;
2. актуальная техническая документация;
3. связанные задачи и ранее принятые решения.

Документация не достовернее кода. Расхождение документации и кода зафиксировать в результате.

## Модель решения

По Jira и документации, до проверки кода, разложить и не смешивать:

- исходное требование;
- текущее поведение, как его описывает аналитик;
- новое поведение;
- компоненты, которые предлагается изменить;
- API, контракты, модели данных, события, интеграции, пользовательские сценарии;
- утверждения о текущей системе, на которых стоит решение.

Четыре метки, не одна куча: **требование**, **подтверждённый current state**, **предположение аналитика**, **предлагаемое решение**.

## Область поиска по репозиториям

Не читать и не искать по всем локальным репозиториям кластера.

Порядок:

```text
требование → затронутые компоненты → конкретные репозитории → конкретные symbols/files → current state
```

1. По Jira, Confluence и модели решения назвать потенциально затронутые компоненты.
2. Сопоставить их с конкретными репозиториями. Открывать только эти репозитории.
3. Внутри репозитория искать entry points, API, модели, обработчики, контракты, symbols и связанные реализации. Репозиторий целиком не читать.
4. Другой репозиторий открывать только если в документации или уже найденном коде есть подтверждённая зависимость или ссылка на другой компонент. У расширения scope должно быть это основание.
5. Нужный компонент лежит в репозитории, которого локально нет и который недоступен через имеющиеся источники — не искать похожую реализацию в других репозиториях. Статус: `Cannot verify`.
6. Нет реализации в просмотренных репозиториях — это не значит, что её нет во всей системе.

Если меняется интерфейс между компонентами, цепочка не заканчивается на producer:

```text
изменяемый компонент / контракт → прямые потребители → их репозитории → текущая обработка
```

Анализ не ограничивать backend / service repository. Компонент не считать незатронутым только потому, что аналитик не включил его в solution scope.

Прямых потребителей искать, если меняются API, контракт, формат запроса или ответа, cardinality ответа, семантика существующих полей, поведение метода, порядок, приоритет или фильтрация возвращаемых данных. К потребителям относятся BFF, web, iOS, Android и другие сервисы.

Репозиторий потребителя открывать, когда он есть локально и есть основание: ссылка в документации, вызов в коде, использование контракта или явная зависимость. Глобальный поиск по кластеру не делать. Нет репозитория и проверить через доступные источники нельзя — `Cannot verify` для этой части, ограничение записать в отчёт. Похожую реализацию в других репозиториях не искать.

## Актуальность локального репозитория

Перед чтением кода выбранного репозитория. Возраст клона — не критерий актуальности. Разные SHA сами по себе не значат, что remote новее.

1. Локальный commit ветки: `git rev-parse HEAD` и `git rev-parse --abbrev-ref HEAD`.
2. Commit той же remote-ветки через GitLab API. Проект — из `origin`. Default branch — из проекта, если ветка не задана. Коммит ветки: `GET /api/v4/projects/<path>/repository/commits/<branch>`. Клиент — `scripts/git_client` из соседнего репозитория `jira-write`, если он есть; иначе HTTPS с `PRIVATE-TOKEN` из `GITLAB_PAT`. Токен не печатать.
3. Сравнить SHA.

SHA совпали — читать локальную копию, не обновлять.

SHA различаются — проверить, можно ли довести локальную ветку до remote через fast-forward. `git fetch origin <branch>` допустим: он не меняет текущую ветку. Fast-forward возможен, только если локальный HEAD — предок remote-коммита (`git merge-base --is-ancestor HEAD origin/<branch>`).

Обновлять только если рабочее дерево чистое (`git status --porcelain` пустой) и fast-forward возможен: `git merge --ff-only origin/<branch>`. После этого анализировать уже обновлённую копию.

Не обновлять и считать актуальность непроверенной, если история разошлась, на локальной ветке есть собственные коммиты, рабочее дерево грязное или состояние нельзя однозначно определить. Локальный код в этом случае не считать гарантированно актуальным. Ограничение записать в файл отчёта. В чат выносить только если оно сужает вывод. Успешную сверку SHA, fetch и отказ от обновления в чат не писать.

Нельзя: менять код, commit, merge не через fast-forward, ветки, push, reset, rebase, force и любые операции, которые могут потерять локальные изменения, любые записи в remote. Разрешены чтение и безопасное обновление локальной копии через fast-forward при чистом дереве.

## Проверки

Только значимые части решения. Нельзя подтвердить по доступным данным — `Cannot verify`, не додумывать.

**Соответствие архитектуре.** Противоречит ли решение потокам данных, контрактам, ответственности компонентов, алгоритмам, модели хранения, интеграциям.

**Реализуемость.** Есть ли предпосылки: данные в нужной точке, интеграция, контракт, способность компонента выполнить ответственность.

**Неподтверждённые утверждения.** То, что в решении подано как факт о текущей системе, но источники это не подтверждают → `Unverified assumptions`.

**Scope.** У каждого существенного технического или архитектурного изменения есть основание: прямое требование, техническое ограничение системы, совместимость или подтверждённое архитектурное ограничение. Иначе — потенциально необоснованное расширение scope.

**Минимальность.** Есть ли более локальный способ закрыть исходное требование без существенного изменения архитектуры или контрактов. Не проектировать этот способ целиком. Отметить, если предложенное изменение существенно шире потребности.

**Контракты и API**, если решение их трогает: структура запроса или ответа, семантика полей, cardinality, backward compatibility, версионирование, прямые потребители, изменения клиентов, другие сценарии того же контракта. Проверки producer недостаточно.

**Поведение потребителя.** Для каждого найденного потребителя смотреть не только десериализацию. Как сейчас обрабатываются данные: один объект или коллекция, пустой результат, fallback, сортировка, приоритеты, фильтрация, переключение элементов, таймеры, анимации, группировка, показ нескольких сущностей, уже существующий механизм с похожей ответственностью, сочетание нового поведения со старыми сценариями. Вывода «контракт можно изменить» недостаточно: потребитель должен понимать новую семантику, а поведение интерфейса должно быть определено. Комбинация двух существующих механизмов, для которой поведение нигде не задано, — замечание.

**Невыбранные варианты.** Вариант в документации не игнорировать только потому, что он ещё обсуждается. Если он меняет контракт, число возвращаемых сущностей, семантику ответа, требует новых клиентских сценариев или заметно расширяет scope — проверить последствия. Варианты с принципиально разным техническим scope — замечание о проработке: вариант нужно выбрать, последствия учесть до готовности задачи.

**Зависимые компоненты.** Отдельно: backend, BFF, web, iOS, Android, другие сервисы-потребители, непроверенные компоненты. Найден, но в решении не рассматривается — отметить. Не писать «не затронут», если реализацию не проверяли.

**Существующие сценарии.** Может ли новое решение изменить уже работающее поведение: комбинации механизмов, fallback, приоритеты, фильтрация, сортировка, кеш, один контракт у разных клиентов, обратная совместимость.

**Producer → contract → consumer.** Если меняется интерфейс между компонентами, проверить обе стороны. Особенно когда затронуты web, iOS или Android.

## Нехватка данных

Статус части: `Cannot verify`. Явно: что не проверено, каких данных нет, какой компонент или репозиторий недоступен, нужно ли подтверждение владельца или разработчика.

## Результат

Полный отчёт — временный файл, не сообщение в чат и не отдельное ревью. Писать только если пользователь выбрал архитектурный анализ. Имя: `architecture-validation-<KEY>.md`. Каталог: `jira/tmp/`, если он есть в workspace; иначе временный каталог вне git. Файл не коммитить, не публиковать, Jira и Confluence им не менять. Записать не удалось — не выдумывать путь, одной фразой сказать об этом и продолжить pipeline.

В файле можно держать current state, proposed change, просмотренные репозитории, branch / commit, files / symbols, связи producer / contract / consumer, затронутые и непроверенные компоненты, неподтверждённые предположения, compatibility risks, ограничения, `Cannot verify`, вопросы на ручное подтверждение, evidence. Замечание как факт — только со ссылкой. Код: repository, branch, file, symbol. Документы: ссылка на Jira или Confluence. Предположение модели — не подтверждённый факт. Пустые разделы не заполнять догадками.

В чат этот файл не вставлять. После анализа pipeline ревью идёт дальше. Короткий статус — только в `review-style.md`, перед общей очередью. Подробности из файла — только по явной просьбе показать архитектурный анализ, полный отчёт или основание вывода.

Actionable-выводы — отдельный список architecture findings с provenance `architecture/current state`. Туда входят: архитектурное противоречие, неучтённая зависимость, несовместимость клиента, проблема контракта, потенциально необоснованный scope, отсутствующее правило поведения, конфликт с существующим сценарием, критичное неподтверждённое предположение, невозможность проверить значимую часть, без которой решение нельзя считать готовым. Documentation findings этим списком не заменять и не сокращать обход документов. Слияние только в `reconciliation.md`, если исправление одно и то же. Одинаковый факт не копировать. Checklist-ревью этот этап не заменяет.

```text
## Architecture validation

### Status
Confirmed | Concerns found | Cannot fully verify

### Current state

### Proposed change

### Architectural conflicts

### Unverified assumptions

### Potentially unnecessary scope

### Affected components

### Compatibility risks

### Questions requiring human clarification
```

`Confirmed` — значимые части сверены с источниками, конфликтов и лишнего scope нет. `Concerns found` — есть конфликт, неподтверждённое существенное предположение, лишний scope, неучтённая зависимость или риск совместимости. `Cannot fully verify` — ключевую часть сверить нельзя. Пустые разделы не заполнять догадками: написать, что по этой проверке замечаний нет, либо что проверка `Cannot verify`.
