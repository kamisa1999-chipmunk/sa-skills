# Reconciliation SA-review

Читать **после** coverage gate и **до** фиксации очереди. Не читать в начале прогона. Пользователю не показывать.

Не полный повторный анализ: не пересобирать карту и не искать новые дефекты «с нуля». Только сверить подтверждённые gap с очередью после группировки и coverage gate.

Очередь нельзя зафиксировать, пока у каждого подтверждённого gap нет ровно одного статуса.

## Что такое подтверждённый gap

Внутренняя запись из проверки evidence (поле `gap`): конкретное расхождение или неясность, по которой уже есть verdict `ISSUE` или `NEEDS_CLARIFICATION`. Сюда же — вопросы, которые добавил coverage gate.

Не считать gap’ом критерий со статусом `OK` или `NOT_APPLICABLE` без расхождения.

Список gap держать в памяти прогона с момента проверки evidence. Не восстанавливать его только из уже сгруппированной очереди: иначе проглоченные при группировке gap некому поймать.

## Статусы

Для каждого подтверждённого gap — ровно один:

| Статус | Когда |
| --- | --- |
| `own finding` | Gap сам стал отдельным блоком очереди |
| `merged into finding N` | Тот же root cause, что у блока N; объединение явное, не молчаливое |
| `NEEDS_CLARIFICATION` | Gap остаётся вопросом в очереди |
| `not an issue` / `obsolete` / `not applicable` | Явно снято: не дефект, устарело или неприменимо, с короткой внутренней причиной |

До этого шага documentation findings и architecture findings хранятся отдельно. У каждого gap есть provenance: `documentation/checklist`, `architecture/current state` или `both`. Provenance пользователю не показывать. Architecture validation не удаляет documentation gap.

`merged into finding N` допустим только если одновременно:

1. это один root cause;
2. исправление одно и то же;
3. не теряется самостоятельное требование, нарушение процесса или вопрос;
4. итоговый finding сохраняет существенные consequences и obligations обоих gap.

Одной темы, одной страницы или одного более широкого finding недостаточно. Разные действия — отдельные findings. Field-level conflict по типу, cardinality, requiredness или смыслу не закрывается отсутствием спецификации, несовместимостью контракта, архитектурным риском, недоопределённым алгоритмом, терминологией или идентификатором сущности.

Не схлопывать, например:

- алгоритм выбора не определён и в решение добавлено бизнес-правило без требования;
- нет спецификации публичного метода и страница BFF описывает внутреннюю реализацию другого компонента вместо ссылки на его спецификацию;
- технически не хватает параметра для AB и результат обязательного анализа AB не зафиксирован в Jira.

Независимые проблемы получают `own finding` или свой `NEEDS_CLARIFICATION`.

Нельзя терять gap только потому, что рядом появился более крупный finding. Отсутствие gap в очереди без статуса — ошибка этого шага, не «значит неважно». Один и тот же факт не повторять дважды. Несколько проблем одной функциональности допустимы, если действия разные.

## Preservation check

Перед фиксацией очереди, пользователю не показывать:

- самостоятельные documentation findings пережили reconciliation;
- у объединённого finding на месте отдельные requirement, consequence и required action;
- field-level conflict между связанными спецификациями не исчез и не поглощён более широким finding;
- вопрос об основании нового бизнес-правила не исчез;
- finding о непроверенном происхождении конкретного алгоритма выбора не исчез;
- общее требование не принято за evidence конкретного priority, fallback или selection rule;
- требование к ownership и к месту фиксации результата не исчезло.

Объединение только по общей теме, при разных исправлениях — разделить обратно. Не начинать ревью заново.

## Если нашли пропуск или неверное слияние

1. Вернуть потерянный gap в очередь (`own finding` или `NEEDS_CLARIFICATION`) либо явно снять его одним из статусов снятия.
2. Если в одном блоке оказались независимые проблемы — разделить на отдельные блоки до фиксации.
3. Не начинать ревью заново и не перечитывать все артефакты.

## Запреты

- не показывать таблицу reconciliation пользователю;
- не писать её в tracked-файлы;
- не использовать `merged into finding N`, чтобы спрятать второй дефект;
- не превращать непроверенный или забытый gap в `not an issue` ради закрытия списка.
